# 3. 「メインスレッドが詰まっている」と、なぜ画面が固まるか

> 所要時間: 読むのに 10 分、演習に 10 分
> ゴール: 処理が動く順番を予想できる。画面が固まったとき、重い処理が順番を譲っていないことが原因かを判定できる
> 前提: JavaScript の短いコードを読める。[1 章](01-quickstart.md)の準備（`npm install`）を済ませている

## 0. 一枚で

| 会話に出る言葉 | 意味 |
|---|---|
| メインスレッド | ページの中で、プログラムの実行と画面の更新を、1 つずつ順に進める係 |
| 詰まっている | 1 つの処理が長く、後ろに並んだ仕事（クリックへの反応、画面の更新）が待たされている |
| 長いタスク | 50 ミリ秒を超えて順番を占有する、1 つの処理 |
| 分割する、譲る | 長い処理を小分けにして、合間に後ろの仕事を通すこと |

ページが届くまでの話は 2 章で終わりです。この章は、届いたページがブラウザの中で動くときの話です。

## 1. 1 つの係が、全部を順にやっている

ページの中の仕事は、**メインスレッド** と呼ばれる 1 つの係が受け持ちます。

元のレポートによると、メインスレッドの仕事は次のとおりです。

| 仕事 | 内容 |
|---|---|
| HTML を読む | 届いた HTML から、ページの構造を組み立てる |
| JavaScript を動かす | 開発者が書いたプログラムのほぼすべて |
| 見た目を計算する | どの要素が何色で、どの大きさか |
| 配置を計算する | どの要素を画面のどこに置くか |
| 描く命令を作る | 何をどの順に描くか |
| 操作を届ける | クリックやキー入力を、プログラムに渡す |

メインスレッドは、同時に 2 つの仕事をしません。1 つを終えてから、次に移ります。

「詰まる」は、ここから起きます。プログラムが長く動いていると、その間は画面の更新も、クリックへの反応も始められません。

## 2. 順番のルール

仕事が 1 つずつ進むなら、どの順に進むかを知っておく必要があります。

JavaScript には、処理を「あとで動かす」ように頼む書き方が 2 つあります。`setTimeout(処理, 待ち時間)` は、待ち時間がたったら動かすように頼みます。`Promise` の `then(処理)` は、前の作業が済んだら動かすように頼みます。

この 2 つと、ふつうの行を混ぜた 4 行を実行します。

<!-- source: examples/03-order.mjs -->
```js
console.log('1. 最初の行');

setTimeout(() => console.log('4. setTimeout(0) に渡した処理'), 0);

Promise.resolve().then(() => console.log('3. Promise の then に渡した処理'));

console.log('2. 最後の行');
```

```sh
node examples/03-order.mjs
```

<!-- output: order -->
```
1. 最初の行
2. 最後の行
3. Promise の then に渡した処理
4. setTimeout(0) に渡した処理
```

書いた順ではなく、番号の順に動きました。`setTimeout` に 0 ミリ秒を指定しても、すぐには動いていません。

順番待ちの 1 つぶんの仕事を、タスクと呼びます。ルールは 3 つです。

1. いま動いているタスクを、最後まで実行する。途中で割り込まれない。
2. タスクが終わったら、`Promise` の `then` に渡した処理（`await` の続きも同じ）を、残らず実行する。
3. そのあとで、次のタスクに移る。`setTimeout` に渡した処理や、クリックへの反応は、ここで順番が来る。

画面の更新も、同じ列に並んで順番を待ちます。更新の機会が来るのは、多くの画面で 1 秒に 60 回（約 16.7 ミリ秒ごと）です。

上の出力は Node.js で実行したものです。同じ 4 行をブラウザの中で動かしても、順番は同じです。

```sh
node examples/03-order-browser.mjs
```

<!-- output: order-browser -->
```
ブラウザ（Chromium）の中で動かした結果
1. 最初の行
2. 最後の行
3. Promise の then に渡した処理
4. setTimeout(0) に渡した処理
```

## 3. 詰まらせてみる

合計 1 秒かかる重い処理を、休まずに続けるプログラムがあります。

<!-- source: examples/03-busy/work-starter.js -->
```js
export async function heavyWork() {
  for (let i = 0; i < 20; i++) {
    compute(50);
  }
}
```

`compute(50)` は、50 ミリ秒のあいだ計算を続ける関数です。それを 20 回繰り返すので、1 秒かかります。

この処理が始まって 0.2 秒たったところで、ページの別のボタンを押します。

```sh
node examples/03-busy.mjs starter
```

<!-- output: busy-starter -->
```
読み込んだファイル: work-starter.js（合計 1 秒の重い処理）
クリックから反応まで: 約 0.8 秒
重い処理の間に画面を更新できた回数: 0 回
判定: ✗ 重い処理が終わるまで、ボタンが反応しない
```

重い処理の 1 秒間、画面は 1 回も更新されませんでした。ボタンは、重い処理の残り（約 0.8 秒）が終わるまで反応しませんでした。

2 節のルール 1 のとおりです。20 回の繰り返しは 1 つのタスクなので、終わるまでクリックへの反応に順番が回りません。

50 ミリ秒を超えるタスクを **長いタスク** と呼びます。操作してから次に画面が更新されるまでの時間は、200 ミリ秒以下が良好の目安とされています（INP という指標）。

この例は 1 秒なので、長いタスクです。「メインスレッドが詰まっている」は、長いタスクが順番を占有している状態を指します。

## 4. 演習: 順番を譲る

<!-- exercise: ex-yield -->

`examples/03-busy/work-starter.js` を書き換えて、重い処理の途中でもボタンが反応するようにしてください。

計算の量は減らしません。`compute(50)` を 20 回呼ぶことは変えずに、次のコマンドの判定を ✓ にします。

```sh
node examples/03-busy.mjs starter
```

ヒントは 2 節のルール 3 です。`setTimeout` に渡した処理は、次のタスクになります。タスクとタスクの間には、クリックへの反応や画面の更新が入れます。

`work-starter.js` には、`pause` という関数を用意してあります。`await pause();` と書くと、いまのタスクをそこで終わりにして、続きを次のタスクに回せます。中身は読めなくてもかまいません。この 1 行を、どこに置くかを考えてください。

自分の目で確かめたいときは、`node examples/03-busy.mjs starter --serve` を実行し、表示された URL をブラウザで開きます。「重い処理を始める」を押してから、すぐに「押してみる」を押します。

<details>
<summary>答え</summary>

繰り返しの中に `await pause();` を 1 行足します。50 ミリ秒ぶん計算するたびに、続きを次のタスクに回すことになります。

<!-- source: examples/03-busy/work-answer.js -->
```js
// いまの処理を終わりにして、続きを「次の順番」に回す
function pause() {
  return new Promise((resolve) => setTimeout(resolve, 0));
}

export async function heavyWork() {
  for (let i = 0; i < 20; i++) {
    compute(50);
    await pause();
  }
}
```

`await pause()` のところで、いまのタスクが終わります。続きは `pause` の中の `setTimeout` を通して、次のタスクになります。

```sh
node examples/03-busy.mjs answer
```

<!-- output: busy-answer -->
```
読み込んだファイル: work-answer.js（合計 1 秒の重い処理）
クリックから反応まで: 100 ミリ秒未満
重い処理の間に画面を更新できた回数: 10 回以上
判定: ✓ 重い処理の途中でも、ボタンが反応する
```

計算の量は同じ 1 秒ぶんです。1 秒の長いタスク 1 つが、50 ミリ秒のタスク 20 個に分かれたので、合間にクリックへの反応と画面の更新が入りました。

余裕があれば、もう 1 つ確かめられます。`pause` の中身から `setTimeout` を外して `Promise` だけにすると（`examples/03-busy/work-promise.js`）、判定は ✗ に戻ります。

```sh
node examples/03-busy.mjs promise
```

<!-- output: busy-promise -->
```
読み込んだファイル: work-promise.js（合計 1 秒の重い処理）
クリックから反応まで: 約 0.8 秒
重い処理の間に画面を更新できた回数: 0 回
判定: ✗ 重い処理が終わるまで、ボタンが反応しない
```

2 節のルール 2 のとおり、`Promise` の続きは次のタスクに移る前に実行されます。タスクが終わらないので、順番を譲ったことになりません。

</details>

## 5. 会話についていくための補足

この節の内容は、この本では動かして確かめていません。元のレポートの説明を短くしたものです。

| 会話に出る言葉 | 意味 |
|---|---|
| コンポジタ | スクロールと、一部のアニメーション（位置をずらす、透明度を変える）を受け持つ別の係。メインスレッドが詰まっていても、これらは動き続ける |
| Web Worker | 重い計算を、メインスレッドとは別の係に任せる仕組み。画面の要素には触れない |
| レイアウト | 1 節の「配置を計算する」のこと。要素の大きさや位置を変えると、やり直しになる |
| INP | 操作してから、次に画面が更新されるまでの時間を測る指標。良好の目安は 200 ミリ秒以下 |

**どの言葉も、「メインスレッドを空けておく」という 1 つの目的につながっています。**

## 6. 理解度チェック

<!-- quiz: order -->
**問 1.** 次のコードは、A・B・C をどの順に表示しますか。

```js
setTimeout(() => console.log('A'), 0);
Promise.resolve().then(() => console.log('B'));
console.log('C');
```

<details>
<summary>答え</summary>

C、B、A の順です。

いまのタスク（C）を最後まで実行し、次に `Promise` の続き（B）を実行し、そのあとで次のタスク（A）に移ります。2 節の例と同じ並びです。

</details>

<!-- quiz: blocked-main -->
**問 2.** あるボタンを押すと、画面が 2 秒固まります。開発者ツールの Network タブを見ると、その間のリクエストは 1 回で、50 ミリ秒で返っています。原因は通信ですか、メインスレッドですか。

<details>
<summary>答え</summary>

メインスレッドです。通信は 50 ミリ秒で終わっているので、残りの時間はページの中の処理が使っています。

ボタンを押したあとの処理が長いタスクになっていて、画面の更新に順番が回っていない、と考えられます。3 節の例と同じ形です。

</details>

<!-- quiz: blocked-main -->
**問 3.** 3 節の `heavyWork` の先頭に、`await pause()` を 1 回だけ足しました。繰り返しの中には足していません。ボタンは反応するようになりますか。

<details>
<summary>答え</summary>

なりません。先頭で 1 回譲っても、そのあとの 20 回の繰り返しは 1 つのタスクのままで、1 秒かかります。

譲るのは、長い処理の途中でなければ意味がありません。4 節の答えは、繰り返しの中で毎回譲っています。

この形は `examples/03-busy/work-once.js` にあり、`node examples/03-busy.mjs once` で判定が ✗ になることを確かめられます。

</details>
